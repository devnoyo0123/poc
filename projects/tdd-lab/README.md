# tdd-lab

이미 구현된 프로덕션 백엔드를 **TDD(테스트 주도 개발)로 처음부터 다시 구현**해보는 실험 프로젝트.

## 🎯 실험 목적

이미 기능이 모두 구현된 백엔드를 대상으로, **처음부터 TDD로 접근했을 때 어떤 차이가 나는지** 관찰한다.

- TDD 사이클(Red → Green → Refactor)이 설계에 미치는 영향
- 테스트 커버리지와 리팩터 안정성
- "구현 먼저" vs "테스트 먼저"의 개발 흐름 차이

## 🔒 비즈니스 로직 노출 방지 원칙 (가장 중요)

이 실험은 **기존 코드를 블랙박스로 취급**한다.

### 참조 허용 (스펙 = 계약)
- 엔티티의 **필드 이름/타입** 선언부 (메서드 본문 제외)
- DTO 클래스의 **필드 이름/타입**
- REST **엔드포인트 시그니처** (HTTP 메서드 + 경로)
- **enum 값** (상태, 타입 등)
- 테이블/컬럼명 (스키마 구조)

### 노출/복사 금지 (비즈니스 로직)
- 서비스/application 메서드의 **내부 구현** (계산식, 알고리즘, 분기, 사이드이펙트 순서)
- 도메인 규칙의 **구체적인 처리 방식**
- **기존 코드를 한 줄도 복사하지 않는다** — 내 방식으로 새로 작성

> 즉, "무엇(What)"은 알되 "어떻게(How)"는 모르는 상태에서, TDD로 How를 새로 발명한다.

## 📈 진행 순서

도메인은 스펙(엔티티 필드/엔드포인트/enum)에서 추출한 이름을 그대로 사용하되, **비즈니스 맥락은 기재하지 않는다**.

1. **Payout** (작게 시작) — 상태 전이 단순, 의존성 최소 → TDD 사이클 안정화
2. **Contract** — 상태 전이 + 검증 규칙 풍부 → 도메인 로직 TDD 진가
3. **Settlement/Aggregation** (시간 허용 시) — 집계/파이프라인 → 가장 극적 비교 포인트
